# Known Issues, Edge Cases & Gotchas

Observed in the real code. "Resolution" = how the code already handles it or what to do.

## Build/tooling
- **`?v=1.0.93` import query strings break static analyzers.** `madge`/`dependency-cruiser` resolve `./foo.js?v=…` to a non-existent path and report **empty** dependencies. *Resolution:* the graph in `agent/graph/` was built by reading imports directly; regenerate the same way. When bumping the version, change it in `package.json`, `service-worker.js` (`APP_VERSION`), `runtime-config.js`/`readiness.js`, **and** every `?v=` import suffix together.
- **`js/ui/siri-wave.js` is effectively orphaned.** No runtime module statically imports it; it's only dynamically imported by `tests/e2e/app-ui.spec.mjs` and precached in `service-worker.js`. Don't assume it's dead — but also don't expect it on the main import graph.

## Signaling fallbacks & failure modes
- **Mock vs production selection.** Runtime flags only activate when `productionSignaling===true` **and** a valid `signalingUrl` exists (`runtime-flags.js`). Otherwise the app silently uses `MockSignalingAdapter` with fake peers — easy to mistake for "it's connected to prod." Force mock on localhost with `?runtime=mock`.
- **`connection-failed` only toasts in production.** In mock mode failures are swallowed by design. WebSocket reconnects with exponential backoff (cap 15 s); a `connected` server message restarts the heartbeat.
- **`protocol:error` code `client_id_in_use`** is surfaced as "signaling lost" — usually two tabs sharing a `sessionStorage` client id is avoided because the id is per-tab, but cloned tabs can collide.

## WebRTC
- **ICE candidates can arrive before the remote description.** `webrtc-transport.js` buffers them in `pendingCandidates` and flushes after `setRemoteDescription`. Don't reorder this.
- **Connection-wait timeouts.** `waitForTransportConnection` (controller, 30 s) rejects on `failed`/`closed` or timeout; the controller then `resetFailedVerification`. `preflight()` does a 450 ms probe to classify direct/relay.
- **No TURN ⇒ relay can fail behind symmetric NAT.** `TurnConfigProvider.getRemoteConfig()` throws if there's no authenticated token and falls back to **STUN only** (Cloudflare). Direct works; relay-needing networks won't. Ensure the server's TURN broker is configured for production.
- **SDP CRLF normalization** (`normalizeSdp`) is required for cross-browser interop; both client and server normalize. Don't strip it.

## Transfer protocol
- **Chunk header/payload ordering is strict.** A JSON `file:chunk` header must be immediately followed by its binary payload. If a new header arrives first, the receiver requests a retry and emits `protocol-error`. Receiver also enforces in-order offsets (gap ⇒ `transfer:retry`).
- **Caps.** 500 MB per session (sender and receiver both reject oversize manifests); chunk 256 KB; receiver-ready timeout 45 s; completion timeout 30 min. Completion only fires once `receivedBytes >= totalBytes` (a late `transfer:complete` is held in `completionPending`). Zero-byte files are valid: the sender loops `offset < file.size` (no chunks) and completion is `0 >= 0` → an empty file is produced. Don't "fix" this by rejecting size-0 manifests.
- **A duplicate `transfer:manifest` must be idempotent.** A lost manifest ack causes the sender to retransmit; the receiver must **re-ack and return** when `this.incoming.has(manifest.id)`, never re-`set` the state (that would zero `receivedBytes` mid-transfer). Regression covered by `tests/data-channel-transfer-protocol.test.mjs`.
- **Peer-controlled filenames are sanitized at storage intake.** `file.name` in a manifest comes from the remote peer; `storage-client.js` runs it through `sanitizeFilename()` (strips path separators/traversal, control + Windows-reserved chars, leading dots) at all three `prepareFile` intake points and the stream `createWriteStream` call. Keep new download/save paths reading the already-sanitized `session.files` entry rather than the raw manifest name.
- **Backpressure.** Sender awaits `bufferedamountlow` when `bufferedAmount` exceeds 8 MB; dropping this risks unbounded memory growth.
- **App control messages need a `type` and must be forwarded.** `handleControlMessage` drops any message without `.type`, and unknown types fall through to a `control` event. `WebRtcTransport` only re-emits events on an explicit allow-list, so `control` had to be added there. The live profile feature sends `{ type: "profile:update", profile }` via `sendControlMessage` → `sendControl`; reuse this pattern (namespaced `type`, forwarded `control`) for new peer-to-peer control JSON rather than inventing a side channel.

## Proximity ceremony
- **Policy updates are revisioned and affect new sessions only.** `RuntimeProximityPolicy` snapshots score/timing onto each session; changing Settings while devices are already running intentionally does not alter them. Stop/retry before comparing revisions. Score weights must total exactly 100 or `PUT /api/proximity-policy` rejects the update.
- **Late-tap grace is not the same as acoustic airtime.** `lateTapGraceMs` controls how long a lone first tap may wait to admit a partner. `acousticWindowMs` controls the coded chirp/listen ceremony after the cohort starts. Keep both explicit when analyzing a delayed-tap failure.
- **A high local score can still fail if final telemetry is one-sided.** If a device shows Audio/Bump/Tilt green and ~90+ score but the server returns `ambiguous_or_nonreciprocal_match`, inspect `proximity:session:telemetry:accepted`, `telemetry:unconfirmed`, and server `proximity:session:telemetry:rejected` events before changing thresholds. The common hidden issue is that the server accepted final telemetry from only one phone, so it had no reciprocal pair to match.
- **Safari mic prompts can be hidden by stale app-local permission cache.** Do not reintroduce a controller shortcut that skips `getUserMedia()` when `webdrop.proximityPermissions.microphone` is `"denied"`. Safari/iOS needs the next user gesture to try the native prompt again; only the acoustic sensor should honor a real browser Permissions API denial.
- **Local pass requires ultrasound + bump + tilt (not score alone).** `hasRequiredPhysicalEvidence` mirrors the server gate so the client doesn't claim "passed" on evidence the server will reject. Changing the score weights without this gate causes false positives.
- **Non-reciprocal acoustic match** (`ambiguous_or_nonreciprocal_match`): one phone heard the chirp, the other didn't. The UI says "realign," not "bump harder" (`proximityServerReasonKey`). Preserve that distinction.
- **Ultrasound needs real hardware + secure context.** ~17.8–19.8 kHz emit/detect requires mic + speaker permission and a high-enough sample rate; some devices/laptops can't reproduce or hear it. The server can fail with `acoustic_not_detected` even when one side worked.
- **Acoustic lanes must stay under the 44.1kHz Nyquist emit cap (the lane-3 silence gotcha).** The client caps emittable frequency at `sampleRate*0.45` (`supportsInaudibleChirp`) = **19,845 Hz on 44.1kHz hardware** (older iPhones, many desktops, some Androids), and `createChirpSamples` silently returns a **silent buffer** (plus `emitChirp` refuses `inaudible-frequency-unsupported`) when a lane exceeds it. The server splits `ACOUSTIC_BAND_START_HZ..ACOUSTIC_BAND_END_HZ` into N lanes by round-robin `bandIndex`. If any lane's top exceeds 19,845, a 44.1kHz phone assigned that lane emits silence and builds *silent decode templates* → `acoustic_not_detected` on ~1-in-N concurrent cohorts, "works on retry" (next session lands on another lane). This bit us in v1.0.104: band 17,800–20,000 / 4 lanes → lane 3 = 19,450–20,000 > 19,845. Fixed to `ACOUSTIC_BAND_END_HZ` **19,800** in v1.0.105 (top lane 19,300–19,800). **Rule: never raise `ACOUSTIC_BAND_END_HZ` above 19,800**, and keep the client monitor defaults + admin band splits (`controller.js`, `admin/readiness.js`) and the `message-schema.js` monitor clamp in sync with it. See ADR-0021.
- **Capture starts before `startAt`; the decoder must be told the lead.** `exchangeCapturedSignatureChirps` (`proximity-engine.js`) starts `startCeremonyCapture` immediately, then waits until `startAt` to emit, so the recording's t=0 precedes the slot grid by `leadMs`. `decodeCeremonyCapture` windows slots from recording t=0, so it needs `slotOffsetMs: leadMs` on every decode call (early-poll *and* final) or a large lead pushes clean chirps outside the drift window. Also size the capture cap as `durationMs + leadMs + 600` or the last slot's tail is truncated. Regression covered by the 1300ms-lead test in `proximity-engine.test.mjs`.
- **iOS permission gotcha.** DeviceMotion/mic prompts must run inside a user gesture. `ensureProximityPermissions()` starts all native prompts **before** awaiting so user activation isn't lost on iPhone Safari. Don't `await` between the gesture and the permission calls.
- **The client acoustic-plan filter must track the server band floor (the dead-lane fossil).** `normalizeAcousticPlan` (`proximity-engine.js`) drops any signature whose `startFrequencyHz` is below a threshold. That threshold MUST be `MIN_INAUDIBLE_FREQUENCY_HZ` (17,500), NOT a hardcoded number. In v1.0.105 it was still `18_500` (the pre-band-expansion floor), so with the 17.8-19.8kHz band's 4 lanes the two lowest lanes (17800-18300, 18300-18800) were filtered out on every client → empty signature plan → the phone never emitted and decoded nothing → guaranteed reciprocal acoustic failure, **regardless of mic health**. Because the server assigns lanes via a server-lifetime `bandIndex % 4` counter, this manifested as "the first 2-3 attempts after a server restart fail, then it works" (the counter walks 0,1,2,3 and only the sub-18.5kHz lanes were dead). Fixed in v1.0.106. If you change the band floor, change BOTH the server band start AND this client filter. See ADR-0022.
- **`session.expiresAt` must cover the failTimer linger, not just the join TTL (the telemetry expiry race).** The server sets `session.expiresAt = creation + proximitySessionTtlMs` (15s) at creation, but the ceremony runs ~10.5-11.75s and the `failTimer` deliberately lingers `matchSlopMs` (5s) past window end so slow phones' final telemetry is still accepted. The telemetry gate rejects `session.expiresAt <= Date.now()` as `session_not_available` — so without extending `expiresAt` at start, valid late telemetry (and ALL telemetry from late-tap-grace sessions whose window ends after creation+TTL) is rejected, producing one-sided telemetry → `ambiguous_or_nonreciprocal_match`. `startProximitySession` now does `session.expiresAt = Math.max(session.expiresAt, session.endsAt + matchSlopMs + 2000)`. Don't reintroduce a creation-only TTL for started sessions. Regression: the two expiry tests in `signaling-hub-proximity-session.test.mjs`. See ADR-0022.
- **Reconcile the AudioContext to the mic track rate AFTER permissions settle, never inside `requestMicrophonePermission`.** `prepareAudioOutput()` creates the context during the permission phase before the mic stream exists (default rate); it must be reconciled to the live track rate (`reconcileContextToTrackRate()`) or the first capture runs a rate-mismatched graph (WebKit resample silences 17.8-19.8kHz). The reconcile CLOSES the context, so doing it inside `requestMicrophonePermission` races `prepareAudioOutput`'s concurrent `resume()`/oscillator (they run together under `Promise.all` in `ensureProximityPermissions`) → `prepareAudioOutput` rejects → `audioOutput.granted=false` → acoustics disabled for the whole ceremony. Do it in the controller's `.then` after all three permission promises settle.
- **The acoustic early-exit must wait for the bump.** `exchangeCapturedSignatureChirps`' early-finish poll accepts a clean partner decode, but the ceremony snapshots motion the moment the acoustic phase returns — early-exiting before the user bumps records `bump=false` and fails the local evidence gate. The exit is therefore gated on `canFinishEarly()` (bump present once motion samples are flowing; bypassed when motion is unavailable). Don't remove the gate to "speed up" pairing: without a bump the early exit only converts a possible success into a guaranteed failure, while continuing to listen improves the decode. Covered by the 3-case early-exit test in `proximity-engine.test.mjs`.
- **Warm up acoustics at the Connect tap (preflight), not only in the sync headroom.** The sync-phase `captureSelfTest` is gated on `startAt - now >= 900`, but the server sends `startAt = now + 700 + stagger` and `stagger` is 0 for the first/only cohort → the self-test is usually skipped, so a first-attempt dead/rate-mismatched capture is never rebuilt in time ("first attempts fail, retries work"). `preflightCapture()` (single-flight) is fired at the tap and runs concurrently with the join window to prove/rebuild the emit→mic→capture loop; the sync self-test is skipped only when a fresh preflight passed. Keep the preflight probe narrowband (~18.5kHz, 150ms) so it can't correlate against a coded-sweep decode in a concurrent cohort. See ADR-0022.
- **The motion snapshot latches bump/tilt from capture start, not from `startAt` — the engine must reset at the window open.** Motion capture begins at permission-resolve time, well before the server's `startAt` (it must: prompts need the user gesture, the sensor needs warm-up), and `MotionProximitySensor.getSnapshot()` latches evidence (`bump ||= …`, `bumpAt` set once). Any handling jolt between the Connect tap and the window — guaranteed on the 2nd device or a reconnect, where cached permissions remove the natural prompt pause — would otherwise stamp a phantom `bump=true` that survives the whole ceremony ("Bump detected" with no bump). `runRealCeremony` therefore calls `this.motion.reset?.()` exactly at `startAt`. Don't remove it, and don't "fix" it by resetting in the controller instead (it can't hit `startAt` precisely; the latch is the problem, not the early capture start). Bump AND tilt must occur during the guided window. Safe with the early-exit gate: samples re-accumulate at ~60Hz and `canFinishEarly` also needs a partner decode. Regression: "a bump latched before the window opens is discarded at startAt" in `proximity-engine.test.mjs`. See ADR-0024.
- **The acoustic winner-margin gate is 2-device-only — never reintroduce it for cohorts.** In a >2 cohort all phones share ONE band, so the runner-up decode is a REAL phone meters away and healthy margins collapse below `ACOUSTIC_WINNER_MARGIN` (field: 0.352 vs 0.324 = 0.028), emptying the eligible list and failing the whole cohort `ambiguous_or_nonreciprocal_match`. `hasReciprocalAcousticEvidence` gates margin on `proximityCohortSize(session) <= 2`; in bigger cohorts identity comes from top-decode reciprocity + the bump-partner veto. See ADR-0025.
- **Cross-cohort wrong-pair matches: the veto must see OTHER sessions' bumps, and matching must wait for them.** Cohorts fill by arrival order, so two pairs tapping together can be split CROSSED, and the crossed pair inside one 2-device cohort looks formally reciprocal with an in-slop bump delta (18-19kHz carries meters). `hasCloserBumpPartner` takes `foreignProximityBumpTimes`, and `tryMatchProximitySession` DEFERS eligible pairs while a concurrent overlapping cohort still owes telemetry — **or while this cohort's own members haven't all reported** (ADR-0026: a 3-device cohort matched a 1406ms-delta pair 2s before the third member's 452ms-away bump arrived). Re-run on every accepted telemetry (`tryMatchStartedProximitySessions`) and force-run in `failUnmatchedProximitySession` at the session's own deadline. Don't remove the force-eval (deferral would starve matches when a phone dies mid-ceremony) and don't match only the telemetry-owning session (deferred sessions would never re-evaluate). See ADR-0025/0026.
- **Never feed the island motion polls before `startAt`, and never let a stale ceremony stop the sensors.** The island's stage ladder is MONOTONIC and maps any `motion.bump` event straight to stage 4 "Bump detected — verifying tilt…"; the sensor latch is only cleared AT `startAt` (ADR-0024), so an ungated pre-window poll shows a phantom "Bump detected" that can never regress (field: connect→disconnect→reconnect with a concurrent pair; stagger widens the pre-window). Both `motionTimer`s gate on `Date.now() >= startAt`. Related: ceremonies capture `ceremonyGeneration` at entry and their `finally` stops the singleton sensors ONLY if still current — island-cancel/disconnect increment the counter and cancel stops sensors itself; without this, a cancelled ceremony's window outlives the cancel and its cleanup kills the retry's motion listener + mic capture mid-window. See ADR-0027.
- **Server teardown must tombstone bumps before destroying telemetry.** The cross-cohort veto reads LIVE sessions only; every teardown path re-evaluates survivors immediately after deleting telemetry, so without `proximityBumpTombstones` (15s TTL) failing one crossed cohort un-vetoes the other in the same tick and matches two strangers deterministically. Any new teardown/eviction path MUST go through `evictProximitySessionMember` or call `recordProximityBumpTombstones` first. Also: same-clientId `registerClient` replacement must pass `preserveProximitySessions: true` (an in-page WS blip is not a departure), and `joinProximitySession` evicts started-session ghosts before admitting to a new cohort. See ADR-0027.
- **A denied motion/mic permission must abort the ceremony BEFORE joining the cohort.** Once iOS sees a denial it auto-rejects every further permission request for the rest of the page session with NO prompt (and `MotionProximitySensor` caches the denial) — only a full page reload recovers. Running the staged bump flow anyway pins the score at 0.34 (acoustic only), fails server-side after ~15s with no hint, and drags the partner into a guaranteed-fail session (the 07:07 field case: four doomed ceremonies in a row). `blockedProximityPermissionKey` (module-level, unit-tested) classifies the block; the anonymous path aborts pre-join with the actionable "reload and allow" message (`proximityErrorMotionDenied`/`proximityErrorMicrophoneDenied`, en/ja). "unsupported" is NOT blocked — those devices use the QR-fallback flows. See ADR-0026.

## Storage (iOS especially)
- **iOS Safari uses the in-memory Blob backend, capped at 128 MB.** `selectBackend` throws `StorageClientError("BLOB_FALLBACK_CAP_EXCEEDED")` past that; non-iOS without streaming throws `STREAM_UNAVAILABLE`. Large transfers to iPhone will fail by design.
- **StreamSaver** download needs its service worker (`vendor/streamsaver/`) and is disabled on iOS.
- **StreamSaver must register its OWN service worker even when the app's root SW exists.** `vendor/streamsaver/mitm.html` `registerWorker()` originally reused whatever `getRegistration('./')` returned — on production hosts that is the app's root-scope SW (which ignores stream messages), so desktop Download buttons stalled silently (writer backpressure, `exportFile` never resolves). Fixed (v1.0.109) to reuse a registration only when its scope is exactly `/vendor/streamsaver/`, else register `sw.js` there. **Untestable on localhost by default** — the app SW only registers off-localhost; to reproduce, manually `register('./service-worker.js')` first.

## PWA / caching
- **Service worker only registers off-localhost.** Local dev never gets SW caching (intentional). A `controllerchange` reload guard prevents infinite reloads on update.
- **`runtime-config.js` is always fetched network-only** (`no-store`) so production toggles/URLs update without a cache bust.
- **Activate precache is tolerant, not all-or-nothing.** `activate` deletes *every* cache then rebuilds the current precache with a per-asset `fetch → if ok cache.put` loop. Do **not** revert to `cache.addAll(ASSETS)`: it rejects atomically if any single asset 404s (e.g. one file renamed in a deploy), and since the old caches are already gone, activate would stall with an empty precache — a broken offline shell.

## Admin test recordings
- **Run history is local to one admin browser.** `webdrop.adminTestRuns.v1` lives in `localStorage`; it is not synchronized to the signaling server. Export/screenshot important evidence before clearing browser data or moving operators.
- **Admin auth must never depend on `prompt()`.** Embedded browsers can disable modal prompts. Production must show the visible session-only **Admin access** form, skip the gitignored local-token URL, and avoid calling `/api/diagnostics-public` until a token exists. Otherwise the page tells operators to paste a token without giving them anywhere to paste it.

## UI / rendering
- **Personalized QR depends on ECC level H.** `DynamicIsland.drawQr` overlays an avatar badge on the *display* QR, which only stays scannable because the code is rendered at level **H**. If you drop it back to "M"/"Q" or enlarge the badge/knockout, re-check `tests/qr-personalized.test.mjs` (it asserts `jsQR` still decodes the badged code). Badge ≈ 24% of the code; knockout = badge + ~1.4 modules.
- **QR avatar images are cached in `qrLogoCache` (module-level `Map`).** A warm badge paints synchronously; a cold one paints on image `load`, guarded by `state === "qr-display"` + matching `currentQrToken` so a stale async load can't draw over a newer code.
- **The island wave canvas must stay `position:absolute` in `.webdrop-island__flow`.** As an in-flow grid child, the auto grid row is sized by the canvas's intrinsic aspect-ratio — which `TileWave.resize()` rewrites from the measured rect. That feedback loop let the canvas stabilize larger than the 116px flow, painting the tile band down over the transfer file name (v1.0.109 fix). Any canvas whose backing store follows its own layout box must be absolutely bound to a fixed-size container.
- **The transfer HUD has no progress bar — the tiles are the bar.** `TileWave.setTransferMode(true)` + `setProgress(ratio)` make tiles past the progress front render dim/desaturated while filled tiles keep the sweep (ADR-0007). `setProgress`/`setTransferMode` must repaint when the rAF loop isn't running (reduced motion / motion-paused) via `#repaintIfStatic` → `renderOnce`, and `#drawStatic` must apply the same dim rule — otherwise paused/reduced-motion users see a frozen 0% fill. Don't reintroduce `.webdrop-island__meter` or re-dim the wave during transfer.
- **No white "halo" behind the island tile-wave.** The blurred radial glow (`.webdrop-island__flow::before`) and the wave `drop-shadow` were removed on purpose — the canvas already supplies per-tile bloom via `shadowBlur`. Don't reintroduce a blurred backdrop; it reads as a dirty halo on the near-black panel.
- **Avatar-carousel icons have no frame disc.** `.avatar-carousel button` is intentionally `background: transparent; box-shadow: none` so the pastel avatar art sits clean on the (dark) settings sheet. The blue selection ring is the separate `::after`.
- **Dark-theme white-halo trap: never use `var(--ink)` in an avatar `box-shadow`.** In dark theme `--ink` is near-white (`#f4f4f2`), so `color-mix(in srgb, var(--ink) X%, transparent)` shadows glow white. Use the theme-stable **`--shadow-ink`** (`#14141a`, defined in `css/base.css :root`) for avatar/icon drop shadows — light theme is unchanged, dark theme gets a real (invisible-on-dark) shadow instead of a halo. Already applied to the radar/self/peer avatars (`orbit.css`) and the sheet avatars (`sheets.css`). Panel/sheet shadows still use `var(--ink)` by design.
- **Scan frame must not show a stale QR.** `showQrScanner` clears `[data-island-qr-canvas]` on entry; otherwise a QR drawn during a prior `qr-display` lingers behind the viewfinder. Detection draws video frames to a *separate* offscreen `this.scanCanvas`, so clearing the display canvas is safe.

## Security/secrets gotcha
- **`js/config/local-admin-token.js` currently holds a real metrics bearer token on this machine.** It is gitignored and must never be committed. See `secrets.md`. If it leaks, rotate `METRICS_API_TOKEN` on the server.

## Hosting on Monaca (gotchas)
- **A WebSocket upgrade refused on origin leaves NO server log.** `signaling-hub.js` answers a disallowed `Origin` with a raw `403` then `socket.destroy()` — no log line, nothing in `journalctl`, nothing in `/api/diagnostics-public`. Client-side it is only a bare close **code 1006** and `signalingStatus: "offline"` → the UI reads **"Nearby service unavailable"**. If a client "can't connect" and the server looks idle, suspect the origin allowlist FIRST. Probe it directly: `curl -H "Origin: <origin>" https://<host>/api/ice-servers` → `403 origin_not_allowed` (bad) vs `401 unauthorized` (origin fine, just needs the bearer).
- **Monaca serves `.mjs` as `application/octet-stream`.** Browsers refuse to evaluate an ES module with a non-JS MIME type, so ONE `.mjs` import kills the entire module graph — `app.js` silently never evaluates and you get a painted-but-dead shell (HTML/CSS render, no identity, no avatar, no signaling) while **every asset still returns HTTP 200**. `scripts/build-monaca.mjs` rewrites `qrcode-generator.mjs` → `.js` for the Monaca package only. Diagnose with `import('./js/app.js')` in the console: "Failed to fetch dynamically imported module" on a 200-ing file means MIME, not 404.
- **Monaca serves the app from two different origins.** `console.monaca.education` is the Cloud IDE preview; the "View on Phone" QR uses `direct-preview-<projectId>.monaca.education`. Allowlisting only the first makes the app work on desktop and fail on phones. **The project id is in the hostname, so it changes on every re-import and per person** — each collaborator needs their own `ALLOWED_ORIGINS` entry (ADR-0031 explains why no wildcard).
- **`/preview-content/...` is session-gated, not public.** Without a Monaca login cookie it returns `200` with a stub body (`postMessage({action:"go-to-login"})`) — standalone that renders a **blank page**. Don't hand that URL to someone as a share link; use Vercel.

## Dynamic-island ceremony timing (gotcha)
- **`island.now()` is `performance.now()` (ms since page load), NOT epoch.** Any server-sent timestamp forwarded into `DynamicIsland` (currently `bumpCueAt`, `queuedUntil` from `proximity:session:start`) is epoch ms and MUST be converted before comparison: `this.now() + (epoch - Date.now())`. Comparing an epoch directly against `this.now()` is always false (`~3e4 >= ~1.78e12`), which silently freezes the stage ladder — the "Bump now" cue and the tilt readout (stages 3–4) never appear and pairing dies on score, while the pill sits on "Exchanging ultrasonic waves…". This was the v1.0.122→v1.0.125 field bug (ADR-0032). Internal timings (`ceremonyStageEnteredAt`, `connectionOpenedAt`, the 900 ms legacy hold) legitimately use `this.now()` and are self-consistent — leave them.
- **Bump DETECTION is independent of the island display.** A user who bumps at the right instant connects even if the island shows the wrong stage — so a broken cue looks *intermittent*, not dead. When debugging "won't pair", separate "did the cue show" (island/client) from "was the bump detected" (engine telemetry: `motion.bump`, `ceremony:complete state`).
